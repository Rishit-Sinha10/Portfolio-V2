### 3. Design Direction: Minimal, Editorial, Premium

The design language is minimalist black and white with carefully controlled contrast.

The result should feel like a well-designed independent software product, not a marketing template.

#### Color palette

Use a restrained neutral palette:

- Main background: `#FFFFFF`
- Secondary background: `#FAFAFA`
- Primary text: `#111111`
- Secondary text: `#666666`
- Subtle borders: `#EAEAEA`
- Strong accent: near-black
- Muted interactive surfaces: `#F3F3F3`

Use color to communicate hierarchy and interaction, not to decorate empty space.

Avoid introducing arbitrary accent colors, colorful gradients, purple-blue AI aesthetics, or different colors for every project.

Small tonal variations are acceptable when they improve depth, separation, or usability.

#### Typography

Use this exact font stack:

`"Inter Variable", -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, Helvetica, Arial, sans-serif`

Use the existing Inter Variable font asset if available and correctly configured. Do not assume the font is installed locally or invent a font file path.

Typography must carry much of the visual identity.

Prioritize:

- Strong editorial hierarchy.
- Carefully controlled font weights.
- Compact but readable headings.
- Intentional line breaks.
- Balanced text widths.
- Excellent paragraph readability.
- Precise spacing between labels, headings, and supporting text.
- Consistent baseline and alignment.

Use large display typography where it creates impact, not simply because oversized headings look fashionable.

Suggested desktop scale:

- Hero heading: approximately 64–88px.
- Section headings: approximately 36–52px.
- Project titles: approximately 24–36px.
- Body text: approximately 16–19px.
- Metadata and labels: approximately 11–13px.

Adapt fluidly to smaller screens. Never force desktop typography onto mobile.

Use medium-weight typography where appropriate rather than making every heading excessively bold.

#### Layout and spacing

- Use a controlled content width, generally around 1000–1120px.
- Allow selected hero and project elements to use a wider composition when justified.
- Use generous whitespace, consistent section spacing, and clear alignment.
- Prefer clean grids, editorial columns, and intentional asymmetry.
- Use subtle horizontal dividers where they improve structure.
- Keep corner radii restrained and consistent.
- Use borders instead of enclosing every section in a card.
- Avoid excessive nested containers and unnecessary decorative panels.

The layout should feel calm, confident, and deliberate.

### 12. Micro-Interactions and Motion

Motion should communicate state, hierarchy, or continuity.

It should never exist merely to make the page look animated.

Use subtle interactions such as:

- Short entrance transitions when sections first appear.
- Gentle opacity and vertical movement on initial load.
- Underline or color transitions on links.
- Restrained project-image transitions.
- Small arrow movement on interactive links.
- Clear focus and pressed states.
- Smooth but predictable anchor navigation.

Motion should be quick and restrained, generally around 150–300ms for small interactions.

Use staggered entrance effects sparingly.

Do not animate every paragraph, icon, border, and section independently.

Avoid:

- Unskippable intro animations.
- Fake loading screens.
- Scroll hijacking.
- Excessive parallax.
- Constantly moving elements.
- Unnecessary sound effects.
- Heavy 3D effects.
- Animation libraries added solely for trivial transitions.

Respect `prefers-reduced-motion`.

If the repository already uses Framer Motion or another animation library, evaluate whether it is justified before adding dependencies.

### 18. Implementation Workflow

Work in the following order:

**Phase 1 — Audit**
Inspect the repository, current design, routes, assets, dependencies, and project information.

**Phase 2 — Design system**
Establish typography, neutral colors, spacing, content width, borders, interactive states, and responsive rules.

**Phase 3 — Homepage**
Implement the header, hero, selected work, about, experience if justified, contact, and footer.

**Phase 4 — Project presentation**
Improve the project index and create or refine case-study pages where appropriate.

**Phase 5 — Interaction and responsive polish**
Implement purposeful micro-interactions, mobile navigation, keyboard accessibility, and reduced-motion behavior.

**Phase 6 — Validation**
Run the build and available checks. Inspect the site at desktop and mobile sizes. Fix visible bugs, broken links, console errors, overflow, and accessibility issues.

**Phase 7 — Final review**
Evaluate the result as a hiring manager, senior frontend engineer, and product designer.

Ask:

- Does the page communicate my role in five seconds?
- Is the visual design distinctive without relying on effects?
- Does the work look real and technically credible?
- Is OpenLink clearly the flagship?
- Are the project descriptions specific and honest?
- Does the mobile experience feel intentionally designed?
- Is the page fast, accessible, and maintainable?
- Does anything look generic, unfinished, or unnecessarily complicated?

Fix the most important issues before declaring completion.
